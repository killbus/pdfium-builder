# Design: Variant-agnostic PDFium builder

## Boundary

`pdfium-mod-wasm` is the private source/build-definition owner. It knows the private variant labels, domains, product-lock policy, and how many outputs must be built. `pdfium-builder` is the public orchestration/distribution owner. It knows only the release-set protocol and opaque public release IDs.

The builder must not turn a private source selector into a public CI dimension. In particular, `BUILD_VARIANT`, `PRODUCT_LOCK`, domain names, customer names, and private `pN` labels must not appear in builder source, workflow configuration, public manifests, artifact names, logs, or tags.

## Source-Owned Release-Set Protocol

The source repository provides a release-set entry point or manifest with a public-safe shape similar to:

```json
{
  "release_set_version": 1,
  "entries": [
    {
      "release_id": "opaque-public-id-a",
      "artifact_path": "dist/opaque-public-id-a",
      "artifact_digest": "sha256:...",
      "source_repository_sha": "...",
      "pdfium_source_sha": "..."
    }
  ]
}
```

The private source manifest may contain additional fields while running, but the boundary adapter must allow-list the public fields above. It must reject or strip private selectors rather than copying them to builder artifacts.

The exact opaque ID format is a source-repository decision. It must not be a reversible encoding of a domain or private variant name, and it must remain stable for the intended publication identity.

## Workflow Data Flow

```text
private source repository
  -> source-owned release-set build/manifest
  -> public-safe release-set adapter
  -> builder resolves opaque release IDs
  -> one candidate artifact per release ID
  -> one evidence record per release ID
  -> all-entry acceptance gate
  -> accepted/<release-id>/build-info.json
  -> release job per release ID
  -> release validation
  -> shared release branch + public-safe tag
```

The builder may use a dynamic matrix generated by a `resolve-release-set` job, but the matrix values must be opaque release IDs. It must not contain the private source variant list.

## Identity Contract

Every public candidate and accepted manifest carries:

```text
release_id
build_timestamp
workflow_run_id
workflow_run_number
workflow_run_attempt
repository
builder_sha
source_repository_sha
pdfium_source_sha
artifact identity
```

`build_type`, `product_lock`, `BUILD_VARIANT`, and private domain metadata are not public builder identity fields. If the source needs to attest to private metadata, the builder may retain a digest or signed opaque attestation, but it must not publish the raw values.

## Contract API Changes

### Release-set resolution

- Add a contract command or helper that validates the source-owned release-set manifest and emits the allow-listed public entries.
- Require unique non-empty release IDs, safe artifact paths, valid SHA-256 digests, and immutable source provenance.
- Reject unknown top-level fields or explicitly strip them before the data reaches public artifacts.

### Candidate and evidence

- Replace `build_type`/variant-specific parameters with `release_id`.
- Use names such as:

```text
pdfium-wasm-candidate-<run-id>-<attempt>-<release-id>
pdfium-wasm-candidate-evidence-<run-id>-<attempt>-<release-id>
build-logs-<run-id>-<attempt>-<release-id>
accepted/<release-id>/build-info.json
```

- Ensure IDs are validated before interpolation into paths or GitHub artifact names.

### Candidate-set acceptance

Acceptance receives the source-derived expected release IDs, verifies exact set equality, validates each evidence record against its release ID and artifact digest, then writes one sanitized accepted manifest per release ID.

### Release validation

Require the release ID in candidate/accepted validation and compare the complete public provenance tuple. A candidate for one release ID must fail validation against another even when all source and workflow SHAs match.

## Release Strategy

- Release concurrency and job selection are keyed by opaque release ID.
- The shared `release` branch remains the distribution branch.
- Tags and package metadata use only the approved public release ID and source revision; no private variant/domain mapping is embedded.
- The promotion script must not infer publication behavior from `build_type` or `product_lock`.

## Compatibility and Migration

- Old `dev`/`prod` artifacts and manifests are rejected because they lack the new public release-set identity.
- There is no fallback from a legacy build type to a release ID.
- Existing immutable revision and preflight checks remain unchanged.
- Rollback is a functional revert; already published public IDs remain unambiguous.

## Main Risks

- **Boundary leakage:** copying the source's raw `build-info.json` into `dist` or acceptance artifacts would reintroduce the leak. The adapter must sanitize before upload.
- **Dynamic matrix visibility:** GitHub job names and logs must use only opaque IDs; do not interpolate raw source manifests.
- **Path injection:** release IDs and artifact paths must be validated before filesystem or artifact operations.
- **Missing source orchestration:** the builder cannot invent the private variant enumeration. The source-owned release-set entry point is a prerequisite and must be versioned/tested as a cross-repository contract.
